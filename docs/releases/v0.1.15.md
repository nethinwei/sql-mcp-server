# v0.1.15

`v0.1.15` 交付 Provider Capability Model：服务声明的硬上限按连接判定其在数据库侧的
保证强度，静默降级变为可见，并可选择严格模式拒绝无法兑现硬限制的配置。同版修复聚合
结果列名跨库不一致，并收掉管理面 4 的测试缺口。设计、评审决议与实施记录见
[设计文档](../design/capability-model.md)。

本版本包含 breaking 变更和一项高危安全修复，升级前请先阅读[迁移](#迁移)。

## 安全修复

- **用户身份伪造（高危）**：配置了 `users` 且开启 `trustProxyHeaders` 时，可信代理后的调用方
  发送 `X-MCP-Role: user:<name>` 就能冒充该用户：获得其直接授权、角色与系统权限（包括
  `sql:execute`）；`${subject.x}` 行策略取的是调用方自填的 `X-MCP-Subject`，可以跨租户读取；
  审计与预算也记在被冒充用户名下。自引入用户身份起的各版本都受影响。现在 `X-MCP-Role`
  只能是角色名，含 `:` 时返回 400；自定义 transport 经 `WithSubject` 注入的同类值得到的是不
  持有授权的主体。用户身份只能由用户 token 或 `X-MCP-User` 建立（TM-010）。
- **mTLS 代理信任半径**：此前 mTLS 下，每个持有 clientCA 签发证书的调用方都能设置身份头。
  新配置 `server.auth.trustedProxyCertSubjects`（叶证书 CN 或 DNS SAN，精确匹配）列出代理的
  证书；其他证书带身份头返回 403，不带身份头时按普通调用方处理（TM-005）。
- 管理面：`Revision.yaml` 脱敏；改自己的密码需要提供当前密码；连续锁定时锁定时长逐次
  翻倍（上限 1 小时）；`tableComments`、`visibility` 显式检查数据源作用域。
- HTTP 请求体须在 30 秒内读完（读完即解除期限，SSE 不受影响）。

## Provider 能力模型

- `core/dialect.Profile` 为每项能力分别给出保证强度（`enforced` / `best_effort` /
  `unsupported`）、证据与原因，取代此前平铺的三个 bool。首批能力键：`write.returning`、
  `cost.explain`、`cost.explain.accurate`、`cost.explain.analyze`、`limit.timeout.read`、
  `limit.timeout.write`、`limit.unkeyedWrite`。
- 强度按连接判定：服务注入的会话设置（`statement_timeout`、`max_execution_time`、
  `ob_query_timeout`、`sql_safe_updates`）被 DSN 覆盖或经 transaction pooler 时如实降级；
  MySQL 的 `max_execution_time` 只作用于 SELECT，写语句在数据库侧没有超时
  （`limit.timeout.write` 为 `unsupported`）。PostgreSQL 在请求超时时由驱动发送 cancel
  request，DSN 覆盖下读写超时仍为 `enforced`；经 transaction pooler 时 cancel request 只在
  pooler 转发时生效，因此为 `best_effort`。
- [兼容矩阵](../provider-compatibility.md#provider-能力)的 Provider 能力表改为由各 provider
  的声明生成（`go generate ./x/providers/all`），三库“连接级 timeout”不再是“未独立验证”。

## 硬限制的告警与严格模式

- 数据源依赖的语句超时：读连接的读；有人能经开启的工具写入时写连接的写，以及写后读、
  读写事务落在写连接上的读；有人能执行受信任过程时执行连接的写；开启时 SQL 逃生通道
  连接的读写。不是 `enforced` 的在启动与热重载时告警（同一进程内只在变化时重复）。
- `cost.requireNativeLimits: true`（默认关闭，可热重载）时这样的配置不能加载：启动失败
  或热重载拒绝并保留当前快照，错误逐条列出数据源、连接、能力、用途与原因。
- 控制台的校验与发布审查对尚未应用的配置按其 DSN 同样判定（不连接数据库，密钥按服务
  自己的解析器解析），严格模式下校验失败、阻止发布。
- 管理 API `providerCapabilities` 与控制台数据源卡片显示服务中连接的保证与未强制的语句
  超时，新版本应用后刷新。能力不进入 MCP 数据面（Agent 看不到）。

## 语句超时

- 注入数据库的语句超时比 `cost.queryTimeout` 少十分之一（至多 1 秒），使数据库通常先于
  请求 deadline 停住语句并报告结果确定。`queryTimeout` 须为 0（不限）或不小于 100ms，
  这样留出的余量是整毫秒数，原生超时也短于请求超时。
- 数据库报告的语句超时（PostgreSQL 57014、MySQL 3024、OceanBase 4012）归类为
  `store.ErrStatementTimeout`：遥测记为 timeout，写入超时按“未生效”处理而不再是
  `OUTCOME_UNKNOWN`；与此前相同，计入熔断。

## 聚合结果列名（修复）

`aggregate_records` 的结果此前以数据库自己的列名为键：PostgreSQL 把同一函数的多个聚合
都命名为 `sum` 等，按列名转成行时互相覆盖、丢失结果；MySQL/OceanBase 的键为
`COUNT(*)`、``SUM(`amount`)``。现由执行器按位置统一命名为 `count`（`count(*)`）与
`<func>_<field>`，生成的 SQL 不变，`allowTemplates`、`rejectTemplates` 与估算反馈的
指纹不受影响。与某个分组字段同名的聚合返回 `INVALID_INPUT`。

## 治理语义与工程化（修复）

- `read_records` 的负数 `limit`/`offset` 返回 `INVALID_INPUT`（此前被当作不限，连同 offset
  一起被丢弃）；codegen 拒绝非法的 Limit 节点和不完整的 insert；`create_record` 的空
  `values`、`aggregate_records` 中重复给出的聚合同样返回 `INVALID_INPUT`。
- `EnforceCap` 对 codegen 生成的 select 收紧或补上紧跟在 ORDER BY 之后的 `LIMIT`，不再外包
  子查询，排序在上限之下保持有效（keyset 分页不再可能跳行或重复）。
- 回滚被他人抢先发布时返回带 `published` 的 `CONFLICT`，控制台随即刷新；控制台 SSE 对同一
  管理员的多个连接共用一次工作区读取。
- `sql-mcp-server healthcheck` 子命令，示例 compose 的 `mcp` 服务配置了健康检查；
  `examples/config.example.yaml` 补齐全部字段，`make docs-check` 检查示例覆盖 schema 的每个
  字段；`RELEASE_VERSION` 默认取 `server.json`，govulncheck 钉版。

## 跨 Provider conformance

`internal/conformance.RunGovernance` 在三库同一 fixture 上经完整工具链运行六项任务：
受治理读、对抗过滤、受治理聚合、全表扫描拒绝、无键写入拒绝与语句超时分类，三库结果
与拒绝码一致。三库另有语句超时与 `sql_safe_updates` 的真实数据库测试
（`Test{PG,MySQL,OB}StatementTimeout`）。

## 管理面

- 管理 API 逐操作越权矩阵：每个查询与变更在四种权限的全部 16 种组合下断言，新增操作未
  登记所需权限即测试失败；登记威胁 TM-014。
- 鉴权先于输入解析：方案的范围统计、预览与应用，工作区的 update/reset/合并草稿，无权限
  的调用方先得到权限拒绝。
- 应用方案与预览一样需要 `admin:read` 与 `admin:write`。
- GraphQL 查询复杂度上限有测试锁定。

## 迁移

完整列表见 [CHANGELOG](../../CHANGELOG.md) 的 0.1.15 Breaking 段。要点：

- **mTLS + 代理头**：只配了 `clientCA` 和 `trustProxyHeaders: true` 的部署，在
  `server.auth.trustedProxyCertSubjects` 中写入网关客户端证书的 CN 或 DNS SAN（或改用
  `trustedProxyCIDRs`），否则配置校验失败。
- **`X-MCP-Role` 不能带主体前缀**：代理若用 `X-MCP-Role: user:<name>` 传递用户，改为
  `X-MCP-User: <name>`。
- **改自己的密码**：管理 API 调用方在 `setAdminPassword` 里提供 `currentPassword`。
- **`cost.queryTimeout`**：小于 100ms 的非零值需要调整。
- **PostgreSQL 经 transaction pooler**：语句超时显示为 `best_effort`，开启
  `cost.requireNativeLimits` 时这样的数据源不能加载。

- **聚合结果键名**：读取 `aggregate_records` 结果的客户端改用 `count` 与
  `<func>_<field>`（如 `sum_amount`、`count_id`）；只有 PostgreSQL 的 `count(*)` 键名不变。
  分组字段名与聚合名相同的请求需要改名。
- **应用方案需要 `admin:read`**：只有 `admin:write` 的管理员（及其配置 MCP 令牌）需要补上
  `admin:read`。
- **语句超时**：数据库侧超时比 `cost.queryTimeout` 早至多 1 秒触发；依赖精确等于
  `queryTimeout` 的部署无需改动配置，但会看到语句稍早停止。
- 启动或热重载出现 `a hard limit is not enforced on the database side` 告警时，按原因调整
  连接（不在 DSN 覆盖超时、为写入在数据库侧配置资源限制、为逃生通道使用独立账号），或
  接受该风险；需要强制时开启 `cost.requireNativeLimits`。
- Go API：`dialect.Dialect.Capabilities()` 返回 `dialect.Profile`；`provider.Provider` 新增
  `Profile()`；`mysql.NewAdapter` 额外返回连接的限制；`cost.NewGateFromCapabilities` 接收
  `dialect.Profile`。

## 已知限制

- 请求 deadline 从调用开始计时（含规划与 EXPLAIN），原生超时只是“通常”先触发；请求
  deadline 先到时，写入仍按 `OUTCOME_UNKNOWN` 报告。
- MySQL 写语句在数据库侧没有超时，服务不代管（不做 `KILL QUERY`，无法保证连接账号的
  权限）；严格模式下有写入的 MySQL 数据源不能加载。
- transaction pooler 下 PostgreSQL 的超时依赖 pooler 转发 cancel request（pgbouncer
  支持），没有容器测试，因此定为 `best_effort`。
- 自助改密的当前密码校验没有单独的失败计数；会话被盗者仍可借此逐个尝试（每次一次
  argon2id 运算）。
- CLI 发布不连接数据库，严格模式的问题由服务在应用时拒绝。
- 控制台卡片显示的是服务中连接的保证；尚未应用的修改在发布审查中判定。
- OIDC / 通用 OAuth2 登录降为 Later；控制台交互判据的外部实测仍未完成。
