# v0.1.17

`v0.1.17` 处理现网在数千张表规模下暴露的稳定性问题，并让 MCP 接口对齐协议的最佳实践。
起因是一次现网事故：定期清理的快照表被删除后，新发布的版本整体加载失败，服务停在旧版本、
被改动的用户全部暂停；失败版本每 5 秒完整重建一次，进程最终不再响应。

本版本**有 breaking 变更**，见[迁移](#迁移)。

## 生产稳定性

- **按实体降级，而不是整版失败**：配置的表或字段在库中已不存在时，只有这些实体不可用
  （`ENTITY_UNAVAILABLE`），其余配置照常加载与热重载；读取不到结构的数据源（不可达、自省
  超时）同样只降级它自己的实体，`--watch` 时按退避重新装配，数据源恢复后自动可用。`serve`
  打开连接时不再 ping 数据库。管理 API `serverStatus.unavailableEntities` /
  `unreachableDatasources` 与控制台“需要关注”列出它们，可一键从工作区移除。
- **失败版本退避重试**：从轮询间隔起翻倍，最长 5 分钟；有新发布时立即尝试。轮询只读已发布
  版本的摘要。
- **运行中表结构变更**：删除实体用到的表或列后，调用返回 `ENTITY_UNAVAILABLE`（此前是无说明
  的 `DATABASE_ERROR`；成本闸门的 EXPLAIN 先碰到时，此前还会误报 `COST_EXCEEDED`），`--watch`
  时服务随即重新装配当前版本，把这些实体标为不可用。这类错误不再计入熔断：此前一张被删的表
  被反复调用，可能让整个数据源熔断。PostgreSQL 修改列类型后缓存的语句计划失效，事务外的调用
  自动重试一次。
- **事务**：事务中任何一条语句失败，事务立即回滚；新增 `transactions.idleTimeout`（默认
  1 分钟），空闲的事务由服务端回滚。两者让 Agent 的事务不再长时间持锁，卡住表结构变更和排在
  其后的所有查询（PostgreSQL 中 DDL 排队会挡住之后对该表的全部查询）。
- **待处理页同步移除已删除的表**：方案同步规则新增 `removeTables`，配置 MCP 预览给出
  `removed`。
- **按调用者的资源限制**：角色与用户的 `limits`（`maxRows`、`maxBytes`、`queryTimeout`、
  `softScore`、`hardScore`、`rejectFullScan`、`rps`、`maxInflight`、会话预算 `budget`），只能
  收紧全局值；超出 `rps` / `maxInflight` 返回 `RATE_LIMITED`。控制台角色页与用户页新增
  “资源限制”。
- **内存与开销**：未设置 `GOMEMLIMIT` 时按容器内存上限的 90% 设置；管理 API 缓存解析后的
  配置（可见性等接口 0.33 s → 0.04 s）。
- **PostgreSQL 统计新鲜度**：此前只认手动 `ANALYZE`、不分 schema，几乎所有表都被当作统计过旧
  扣 15 分，带 LIMIT 的顺序扫描因此被软拒绝且无法通过重试解决。现在 autovacuum 的分析同样
  算数，按 schema 判断，不超过 64 KiB 的小表不扣分。

## MCP 协议

- **结构化输出**：成功结果同时给出 `structuredContent`，文本是同一份 JSON；`tools/list` 为每个
  工具声明 `outputSchema`。返回行的工具为 `{"result": [...]}`，其余工具直接给出对象。
- **工具注解与说明**：`title`、`readOnlyHint` / `destructiveHint` / `idempotentHint`、
  `openWorldHint: false`；描述写明用法、返回形状与常见拒绝；服务端 `instructions` 说明先用
  `describe_entities` 查找实体以及如何按拒绝码处理。输入 schema 顶层 `additionalProperties:
  false`。
- **大规模下的发现**：`describe_entities` 列表分页（默认 100、上限 500）并支持 `search`、
  `datasource`；资源 `sql-mcp://schema` 改为摘要，单实体详情在模板
  `sql-mcp://schema/{entity}`。几千个实体时，列表从约 150 KB 降到约 18 KB，资源从约 4 MB 降到
  不到 1 KB。
- **拒绝码**：新增 `OVERLOADED`（服务过载）与 `DATASOURCE_UNAVAILABLE`（数据源熔断），可重试；
  此前是协议级错误。事务内失败的拒绝带 `constraints.transaction: "rolledBack"`。
- **会话**：服务端已不持有的会话返回 404（此前 403），客户端按协议自动重新建立会话，解决
  “用一阵就不能用”；新增 `server.sessionTimeout`（默认 30 分钟，需重启）；用户被吊销或
  `subject` 改变时立即关闭其会话；断线续传缓存按会话公平淘汰；`/mcp` 拒绝跨源浏览器请求。
- **存储过程工具名**：改为可读的 `procedure_<过程名>`，只有重名时才加哈希后缀。

## 迁移

1. **工具结果文本**：优先读 `structuredContent`。解析文本的客户端：返回行的工具改读
   `text["result"]`；单对象结果（写入、事务、`execute_sql`、`describe_entities`）去掉 `[0]`。
2. **`describe_entities` 列表**：读 `entities`，有 `nextOffset` 时作为 `offset` 取下一页，
   或直接用 `search` 查找。
3. **schema 资源**：先用 `describe_entities` 找到实体，再读 `sql-mcp://schema/<实体>`。
4. **存储过程工具名**：按 `tools/list` 的新名称调用，更新写死旧名（带哈希）的客户端与脚本。
5. **事务**：语句失败后事务已回滚，需重新开启并重做写入；需要较长思考时间的场景调大
   `transactions.idleTimeout`。
6. 新配置项均有默认值，现有配置无需修改即可加载。

## 已知限制

- 运行中的表结构变更只有在 `--watch`（配置存储模式）下才会自动重新装配；文件配置要等下次
  重载。
- 迁移脚本仍应设置锁等待上限（PostgreSQL `lock_timeout`，MySQL `lock_wait_timeout`），见
  [运维 · 表结构变更](../operations.md#表结构变更)。
- 未实现 OAuth 受保护资源元数据与进度通知。

`make ci`（fmt、vet、lint、race test、coverage、govulncheck、docs-check）、控制台
vitest / vue-tsc / lint、MCP e2e 与 PostgreSQL、MySQL、OceanBase integration 全绿。跨库一致性
套件新增“表结构变更”任务（空闲事务释放 DDL、事务内缺列回滚、删表降级，三库同一答案）；新增
PostgreSQL 统计新鲜度集成测试。在 3000 张表、12 个角色的本地实例上逐项验证了缺表缺列降级、
运行中删列后的重新装配、分页与结构化结果、跨源拒绝和会话超时后的自动重连。
