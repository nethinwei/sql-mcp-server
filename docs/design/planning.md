# 设计评审：批量配置——目录、方案、模板与配置 MCP

状态：已实现（控制台“数据源与导入”“按规则配置”“待处理”“Agent 接入”）。

## 背景与问题

现网有几百个库，“数据源 → 库 → 表 → 实体 → 授权”逐项操作效率很低：首屏被连接
信息占满，搜索范围不清楚，批量操作靠逐个勾选，导入前看不到结果，维护阶段（新
字段、新表、配置偏差）仍要逐表检查。扫描结果只保存在进程内存里，重启或换副本就
没了。

## 目标与非目标

目标：

- 让“方案”成为批量配置的核心对象：确定范围 → 设置规则 → 生成方案 → 检查例外
  → 加入工作区 → 检查并发布。控制台页面、保存的模板、配置 MCP 得到同一种方案；
- 规则只在服务端计算（业务规则只在服务层实现，入口只做参数、身份、输出），
  页面与 Agent 的结果一致；
- 扫描结果持久化到配置库，支持跨库检索、服务端分页，结构详情按需读取；
- 例外不被静默吞掉：每一条“没做到”都在报告里有一项。

非目标：

- 服务端不调用大模型。自然语言由客户端侧 Agent 转成方案 JSON，服务端只做确定性
  计算；
- 配置 MCP 不提供发布工具，发布始终由人在控制台完成；
- 方案不删除实体，也不修改数据源。

## 服务分层（结论）

- 包 `x/admin/configapp` 是管理面的配置服务：目录、扫描与扫描批次（批次跨进程的
  租约、心跳、接管与重试在 `x/leasing`）、方案预览与草稿、模板、待处理、管理员令牌，
  以及版本差异、权限模拟与版本列表。鉴权（权限与令牌的数据源范围）、脱敏、审核与
  业务规则都在这里；`x/admin/graph`（GraphQL）与
  `x/admin/configmcp`（配置 MCP）只做参数、身份与输出的适配，MCP 不再经过
  GraphQL resolver。
- 服务的结果与输入类型（目录页、方案报告、扫描批次、令牌等）同时是 GraphQL 的类型：
  `x/admin/graph/app_types.go` 以同名别名引入，gqlgen 按名字绑定，不需要两套转换；
  只有引用控制台编辑模型的结果（方案预览中的实体、角色、用户，导入表的候选实体）
  由 graph 转换。gqlgen 生成的 resolver 签名带包名，`internal/fmtcheck` 只对
  `*.resolvers.go` 中的 resolver 签名行豁免行宽。

## 目录（结论）

- 包 `x/catalog`：扫描结果的稳定 JSON 形式（`Table`：列、键、索引、外键、视图、
  触发器），与运行时 `entity.Entity` 相互转换；`Store` 接口按数据源的读连接
  （`Source.ID()`：数据源名、驱动与 DSN 的摘要，不含 DSN 明文）保存库列表与每个
  库最近一次扫描；`MemoryStore` 供测试，`catalogtest` 是一致性套件。
- 配置库 schema 版本 3 新增 `smcp_catalog_lists`、`smcp_catalog_schemas`
  （每个库一行，JSON payload），以及模板、令牌与待处理状态的表（见下），四种后端
  都跑一致性套件。
- `x/admin/configapp.Scans` 写穿配置库，进程内按（源, 库, 扫描时间）缓存解码结果：
  每次读取先查版本（不含 payload），只重新读取变化的库。因此重启后结果仍在，
  另一个副本扫描的结果也能读到。数据源改连到别的数据库后，旧源的结果按“读取配置
  之前保存的”规则清理，与此前的进程内语义一致。
- `catalog(input)` 在服务端按数据源、库（通配）、表名（通配）、关键字、状态、
  字段差异过滤并分页；`catalogTable(ref)` 返回一张表的完整结构与候选实体；
  `catalogLinks(ref)` 返回它引用的表和引用它的表（列表里的数量与浮层详情同源）。
  状态相对草稿（控制台工作区）计算：`NEW` 未导入、`WORKSPACE` 工作区未发布、
  `PUBLISHED` 已发布；字段差异单独给出（新增列与缺失字段），每行带扫描时间
  （只作展示：表结构是否变化与扫描时间无关，不按时间标记过期）。
- 每张表的状态与字段差异按“扫描指纹 + 草稿内容哈希 + 已发布版本”算一次，存为共享
  索引（`configplan.Index`，同时统计每张表被多少外键引用）；一个筛选（除状态外）
  只在索引上过滤，结果存为行在索引中的位置（每行 4 字节），翻页时才取出该页的行。
  翻页、切换状态、条件计数（`planScope`）、待处理和多个管理员看同一筛选都复用同一
  索引；新扫描、草稿修改或发布都会换键。两个缓存都按内存预算淘汰最久未用的项
  （索引 128 MiB、筛选 32 MiB），同一个键并发未命中只计算一次，其余请求等待结果。
  每个数据源的目录按各库扫描时间缓存，不必每次重建。索引过滤与 `configplan.Rows`
  逐项一致由随机测试保证。
- 扫描批次：`startScanBatch` 在服务端排队扫描多个库（每次 2 个，经同一个扫描
  worker 池），关掉控制台也会继续；`scanBatches` 返回进度（各状态的库数，由
  `GROUP BY batch_id, state` 计数，不读各库的行；问到 `items` 时逐批读），
  `scanBatch` 返回一个批次及每个库的成败与错误（控制台轮询只问计数，再逐批读条目，
  已结束批次的条目不再变化，只读一次），`cancelScanBatch` 停止，`retryScanBatch` 把失败与未完成的库作为新批次重扫。
  批次是 `smcp_scan_batches` 的一行，每个库是 `smcp_scan_batch_items` 的一行
  （schema 版本 4，版本 3 的批次进度在升级时迁移过来）
  （状态、错误、已扫描次数、最早重试时间），所有副本都能看到。每个库的状态只沿
  pending → running → done / failed / pending（重试）迁移，批次结束时把仍是
  pending 与 running 的库置为 canceled，与结束在同一事务内完成。执行批次的一次运行
  是所有者（进程标识 + 运行标识，同一进程再次接管也是新的运行）：每次迁移
  （`MoveItem`）与结束（`FinishBatch`）都在一个事务里先以“仍是该所有者且批次
  未结束”为条件写批次行的心跳（锁住该行，接管须等它提交），再写库的状态，所以
  暂停后恢复的旧运行写不进任何东西，并在发现后停止。所有者每 5 秒续一次心跳，取消
  请求写入批次，所有者据此停止；30 秒没有心跳（进程重启或退出）时，任一进程按当前
  已发布配置接管批次（列出未结束批次时只读批次行与计数，认领成功后才读该批次
  的库），把上一所有者正在扫描的库放回 pending 后继续。写状态时配置库
  出错（不是状态冲突）会退避重试（共 4 次）；出错的写入可能已经提交（应答丢失），
  所以重试发现该库已不在原状态时会读回它，与要写的完全一致才算写入成功，读不到则
  停止。仍失败时本次运行停止，但不结束批次、不取消任何库，批次保持最后写入的状态，
  心跳过期后由任一进程（包括本进程）接管；接管时若不能把正在扫描的库放回 pending，
  也放弃这次接管，不运行批次。扫描失败的库在
  5 秒、10 秒后自动重试，最多扫描 3 次，最后一次的错误留在该库上。每个数据源最多
  4 个未完成批次、每批最多 5000 个库，由 `CreateBatch` 在同一事务内（配置库锁行）
  计数并创建，并发请求与多副本不能一起越过上限；请求可带 `requestKey`（控制台每次
  发起时生成），同一管理员在同一数据源用同一键再次请求得到原来的批次，不会重复扫描；
  同一键请求了不同的库时报错，另一位管理员的同名键各自独立。以上在四种
  配置库上跑 `catalogtest` 一致性套件（`MoveItems`、`BatchRequestKeys`、
  `CreateBatchQuota` 等）。
- 选择：控制台的“选择全部匹配”保存的是筛选条件加排除集合，不把几万个表引用传到
  浏览器；导入或交给方案页时转成方案的 `scope` + `exclude`。这是动态范围：作用时
  取筛选当时匹配的表。新扫描或工作区变化使匹配数变化时，控制台更新数量并要求确认
  新范围后才能导入或交给方案页。切换到别的筛选时这项选择不能就地调整（会提示并
  提供“回到所选筛选”）。

## 方案（结论）

包 `x/configplan`，纯计算，不访问数据库。为大规模计算做了这些处理：范围先编译
（列表转为集合、通配模式小写化，不含通配符的直接比较），先按表本身的条件过滤再计算
状态与字段差异；排除列表、变化汇总的实体去重都用集合；字段规则预编译；引用解析在
导入后只构建一次；“字段被谁使用”（键、访问策略、关系两端、授权行范围）一次建成
反向索引，同步删除字段时直接查；候选实体只为需要的表生成（命名仍在整个数据源上
计算，反向关系直接由外键推导，与全部生成时逐项相同，由随机测试保证）：

```text
Plan = { scope, import, grants, fields, sync, exclude, names }
Evaluate(Input{Base, Published, Sources, Denied, Review, Missing, MissingFields, MissingRowColumns}, Plan) → Proposal
Proposal = { Config（Base 应用后）, Entities（新增或修改）, Added, Removed, Roles, Users, Report }
```

- `exclude`：按 `datasource.schema.table` 排除表；写了任何扫描都没有找到的表（拼错或已删除）时
  整个方案被拒绝，否则方案会作用到本想排除的表上；
- `scope`：`datasources`、`schemas`/`tables`（`*` `?` 通配，不区分大小写）、
  `search`、`status`、`drift`、`refs`（显式表）、`entities`（已配置实体的 ID，只选
  它们的表，已不存在的表也按它判定），条件取交集；
- `import`：为范围内未导入的表新增零权限实体。命名、序号与外键关系由
  `Candidates` 计算（与导入页同一份代码）：名称取表名，同一数据源同一库内被占用
  时加序号，`names` 可以指定；指向没有实体的表的外键不生成关系；
- `grants`：`role:<名>`（不存在时新建）或 `user:<名>`（不存在则报告例外），
  动作限 read/aggregate/create/update/delete，可用字段通配限定字段范围，可带行
  过滤。已有同字段同行范围的授权时只补缺少的动作，否则新增一条授权；没有能定位行
  的键时不授予 update/delete；
- `fields`：按列名（及可选类型）通配隐藏或脱敏字段；
- `sync`：按数据库现状新增字段（可默认隐藏）、移除已不存在的字段；授权中的字段
  列表随之移除，仍被主键、唯一键、关系、租户策略或行范围引用的字段不移除，报告
  例外；`removeTables` 移除表已不存在的实体（所在库扫描过却没有该表，或运行中的服务
  发现缺表；未扫描的库不判定），连同指向它们的授权、关系与 `affects`
  （`configrefs.Retarget`，与控制台删除实体相同），`exclude` 中的表保留；
  `keys`（v0.1.20 起）把表的主键与可标识行的唯一键设为扫描结果（`syncKeys`），把
  实体的 table/view 类型设为扫描结果（`syncKind`）；视图保留配置中声明的键。键不再
  包含的列仍被某个关系用作连接列时报告 `keyReferenced`（confirm），键变为空时报告
  去掉写动作的 `noKey`；键的列不是实体的字段（同步也不新增）时不同步该键，报告
  `keyNotField`（confirm）。关系**只报告不修改**：配置不记录关系是否由外键导入，外键
  没有对应关系时报告 `relationshipNew`，以导入命名方式命名（目标实体名或加序号）却
  没有外键对应的关系报告 `relationshipStale`，均为 info；手写关系不受影响。
  运行中的服务发现的缺列（`Input.MissingFields`）只用于范围内未扫描的表（扫描过的
  表以扫描为准），同样生成 `syncRemove`；行范围引用而非字段的列缺失
  （`Input.MissingRowColumns`）不能由同步修复，报告 `rowColumnMissing`（confirm），
  需要管理员修改租户策略、行策略或授权行范围；
- 顺序：导入 → 同步（先键与类型，再字段，最后移除不存在的表）→ 字段规则 → 授权，因此字段规则覆盖同步新增的字段，同一方案
  重复执行第二次没有任何修改（性质测试保证）；
- 报告：范围内表数、排除数、所依据扫描的时间范围、按库计数、合并后的变化（同类
  变化一行，如“授予 role:analyst 读取 · 12 个实体”，可钻取到每个实体的前后差异）、
  例外、范围内未扫描的库。例外分三级：
  - `block`（阻断，不能加入工作区或保存草稿）：目前没有规则产生它，结果校验不
    通过时同样阻断；
  - `confirm`（需确认，控制台要求勾选“已核对”，MCP 要求 Agent 向管理员报告）：
    `unknownUser`、`noFields`（字段范围没有匹配的字段）、`grantFieldsEmptied`
    （同步移除了授权列出的全部字段）、`referenced`、`denied`、`review`、
    `keyReferenced`、`keyNotField`、`rowColumnMissing`，以及去掉了写动作的 `noKey`；
  - `info`（提示）：`renamed`、`sideEffects`、`relationshipDropped`、`relationshipNew`、
    `relationshipStale`、只读的
    `noKey`，以及 `qualified`：新增实体会让已有的简写引用（授权、关系目标、
    `affects`）指向多个实体时，方案把它们改成被引用实体的 ID，与控制台手工导入
    时自动限定引用的做法一致。
  带 `ref` 的例外可以排除对应的表（逐条或按类）重新计算，排除可以撤销；
- `Proposal.Edit()` 转成 `configedit.Edit`，管理 API 在草稿 payload 上应用并走
  完整的配置链校验，同时给出需要重启的变更与连接权限警告（“什么时候生效”）。

## 入口（结论）

- **工作区计算上下文**：目录状态、范围统计、单表详情和方案预览都基于调用者在服务端
  的工作区（控制台先写出尚未写出的修改，`workspace.read`），不按“有没有修改”去判断
  是否等于已发布版本：载入的草稿本身就是基准。预览绑定到计算时的基准与内容
  （`contextKey`），变化后必须重新计算。读取单表结构等异步请求统一区分加载中、
  成功、未找到与失败，只采用最新一次请求；单表同步只在读到表结构后计算差异并允许
  应用，找不到表时报错而不是当作所有字段都已删除。
- **控制台**：方案页先选任务（导入、授权、隐藏或脱敏、同步），再定范围：条件
  同时满足，`planScope` 实时给出命中数、样例与每个条件单独的命中数；授权可限定
  字段与行范围。`previewPlan(plan, draft)` 返回 `planId`、报告、变化后的实体与
  角色/用户（授权的实体引用统一为 ID）和校验结果；只采用最新一次计算，结果绑定
  到计算时的方案与工作区内容，二者变化后必须重新计算。“加入工作区”先写出本地
  未写的修改，再调用 `applyPlan`（与 Agent 的 `plan_apply` 是同一段服务端逻辑，见
  “工作区”），方案改动的项直接写进服务端的工作区，之后照常检查并发布。新建方案默认导入；载入的模板按其内容（未写 `import` 即
  不导入）。
- **模板**：`smcp_plan_templates` 保存当前版本，`smcp_plan_template_versions`
  保存每个版本（作者、时间）。`savePlanTemplate` 的 `expectedVersion` 为空时新建
  （重名失败），否则只在仍是该版本时保存，期间被他人保存则返回 `CONFLICT`；控制台
  区分“更新”和“另存为”，可查看与载入历史版本。
- **待处理**：“重复执行”的模板不会自动改动工作区，`pending` 每次按当前目录重新
  计算：有修改或有未能应用的规则（`confirm`/`block` 例外）的模板、字段有差异的表、
  表已不存在的实体（`goneTables`，可在控制台多选后从工作区移除；这两类各最多列出
  200 项，未处理的在前，其余只计数：`moreDriftTables`/`moreGoneTables`），
  每项一个键（对象 + 情况摘要），可设负责人、稍后处理（到期重新打开）或忽略（必须
  写原因），每次变更写入 `smcp_pending_log`；情况变化（新匹配、新差异）后键随之
  变化，重新打开。未导入的表、未扫描的库、从未列出库的数据源只给出数量和跳转入口，
  没有处理状态。模板的方案在待处理中以审核方式预览（`previewPlan` 的 `review`），
  授权覆盖的每张新表都作为需确认例外列出。已无法执行的模板（如 `exclude` 指向已删除的表）
  带 `error` 列出，不影响其他待处理项。字段通配（`fields: ["*"]` 等）的授权随表字段
  变化更新同一条授权（操作与行过滤相同、原字段是新字段的子集），不追加新授权。
- **配置 MCP**：`/admin/mcp`（Streamable HTTP，无状态），`Authorization: Bearer`
  使用管理员在控制台为每个客户端生成的令牌（`smcp_admin_tokens` 只存哈希；可命名、
  设有效期，记录最近使用时间，每人最多 20 个，单独吊销；过期、吊销或账号停用后
  立即失效），以该管理员当前的权限调用与控制台相同的配置服务，每次调用记录日志
  （工具、管理员、客户端）。令牌可以限定数据源（不设只读：令牌本来就不能发布，
  它应用的方案也要人在控制台确认后发布；早先创建的只读令牌一律拒绝使用，不会变成
  可写）：目录、方案范围、扫描与待处理只到这些数据源；方案范围
  不写数据源时取令牌的，写了别的数据源则拒绝；`plan_scope` 每个条件单独的命中数也
  只在这些数据源内统计；同一管理员其他令牌或会话做的预览快照，只有其范围全在本令牌
  的数据源内才能读取；跨数据源的差异、模拟、版本列表、模板版本与待处理处理记录不可读）。工具：
  - `catalog_search`、`catalog_table`、`catalog_links`、`plan_scope`；
  - `scan_schemas`（服务端扫描批次，默认扫描所有未扫描的库）、`scan_status`（读取
    最近的批次及其各库状态，每批最多列 100 个库、未完成的在前，其余计入 `moreItems`）；
  - `plan_preview` 针对管理员的工作区（服务端保存的那一份，见下）预览，只返回摘要（`planId`、计数、按类与级别的例外数、需确认例外的
    ID、校验），接受 `review: true` 以审核方式列出授权覆盖的每张新表。预览结果按
    `planId` 为预览者保留 15 分钟（最近 32 个）：`plan_details` 只带 `planId`，
    从这份快照按段分页读取，不重新计算，翻页期间的新扫描或发布不会让各页不一致：
    `changes` 只给每组变化涉及的实体数与序号，`changeEntities` 按序号分页读取一组
    变化的实体，另有 `exceptions`（带 ID，可按类与级别筛选）、`added`、`entities`、
    `objects`；
  - 预览与应用在服务入口先校验并规范化方案（动作转小写、排序、去重；受限令牌补上
    数据源），再计算 `planId`，同一方案无论怎么书写，预览与应用得到同一个标识；
  - `plan_apply`：Agent 的操作等同于管理员本人操作，不生成版本。`planId` 须是调用者
    对同一方案的预览（快照仍保留；已过期则要求方案按当前工作区计算仍得到它），应用时
    针对当前工作区重新计算：基于同一版本一起预览的多个方案可以依次应用，后一个叠加
    在前一个之上；出现阻断例外、校验失败或新的需确认例外则要求重新预览。还要用
    `confirmed` 列出管理员确认过的每个需确认例外的 ID（例外 ID 由类型、表、实体与
    详情决定），少列一个当前的、或列出预览与当前都没有的，都拒绝。通过后方案改动
    的项直接写进管理员的工作区（见“工作区”），附一条来源说明（令牌名与 `comment`），
    返回写入的项；
  - `plan_templates`、`pending`、`diff`、`simulate`、`revisions`。`diff` 与控制台
    共用 `revisionops.Diff`：生成前对两侧配置结构化脱敏，DSN 密码与 HTTP token 不会
    出现在任何一行（含上下文行），变化了的标为 `(changed)`。
  没有发布与回滚工具。
- **工作区**：每个管理员一份，保存在服务端，像代码的工作目录：管理员（在任何一个
  控制台）和他的 Agent（他的令牌）直接写同一份，发布相当于提交。模型、不变量、合并
  规则与操作见 [versioning.md](versioning.md)。与方案相关的部分：
  - `plan_apply` 与控制台的“加入工作区”（`applyPlan`）是同一段服务端逻辑：针对当前
    工作区计算方案，把改动的项按条件写入（`WriteItems`），其余项原样保留；控制台关着
    也照样写入，打开即看到；
  - 推送 `event: workspace` 在工作区被写入时通知控制台读取；Agent 写入时控制台提示
    是哪个 Agent 及其说明，说明供“检查并发布”预填；
  - 其他管理员保存的草稿仍是版本：`drafts` 查询列出所有草稿及服务端沿父链求得的
    基准版本，可“在工作区审核”（`mergeDraft`）或丢弃（`discardDraft`）。控制台绑定
    到登录的管理员，换账户即丢弃内存状态并停止旧的同步。

## 性能（实测，Apple M5）

500 个库 × 100 张表（同名表分布在各库，模拟分库分表）：

- 目录筛选（不含缓存）：约 36 ms（`BenchmarkRowsLargeCatalog`）；经 SQLite 配置库
  首次读取需解码全部 5 万张表约 140 ms，之后同一筛选翻页约 2 ms、每页分配约
  0.6 MB（`BenchmarkCatalogPage`，在 `x/admin/configapp`；共享索引之前约 3 ms、
  10 MB）；
- 并发翻页（`BenchmarkCatalogPageParallel`，GOMAXPROCS=10 个 goroutine 同时请求，
  一半请求用从未出现过的筛选、不命中筛选缓存（仍复用索引），另一半命中）：吞吐约
  每 2.9 ms 完成一个请求（ns/op 是总耗时除以请求数，不是单次延迟）；逐请求计时的
  延迟 p50 约 19 ms、p95 约 32 ms（共享索引之前 30 / 64 ms）；
- 导入 4500 张表并授权、脱敏：约 100 ms、每次累计分配约 190 MB
  （`BenchmarkEvaluateLargePlan`；按需生成候选与引用索引之前约 200 ms、380 MB）。

为此修正了 `introspect.Catalog.Lookup`：指定库名时不再复制所有同名表。

## 安全影响与验收

- 方案只能新增零权限实体与显式规则中的授权；新表进入已有授权在重复模板中必须
  审核（`review` 例外）；
- 扫描批次与待处理状态的变更需要 `admin:write`（与扫描一致）；目录、范围统计、方案
  预览与应用需要 `admin:read` 与 `admin:write`，且先鉴权再解析输入；模板
  列表、版本与处理记录需要 `admin:read`；令牌对应管理员自己的权限，可限定部分数据源，只显示一次，只能列出和吊销自己的令牌（不能用令牌管理令牌）；
- 会话 Cookie 不能访问 `/admin/mcp`，令牌也不能访问控制台 API；
- 验收：`x/configplan` 表驱动与随机性质测试（结果总能通过校验、重复执行不再修改、
  每个应授予而未授予的授权都有例外，并用变异验证测试有效），目录与模板/令牌在
  SQLite、PostgreSQL、MySQL、OceanBase 上的一致性套件，`x/admin/configmcp` 端到端
  测试（无发布工具、预览不一致时拒绝保存、在草稿上继续、只读管理员不能保存草稿、
  过期与停用账号的令牌失效、记录使用时间）；控制台用乱序响应、筛选快照与模板载入
  语义的单元测试覆盖操作链路。
